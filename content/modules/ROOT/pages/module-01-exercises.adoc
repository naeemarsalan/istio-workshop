= Module 1: Exercises
:hardbreaks-option:

This exercise section provides hands-on practice with OpenShift Service Mesh 3. You will learn how to enable sidecar injection and configure mutual TLS (mTLS) for your applications.

== Prerequisites

Before starting these exercises, ensure you have:

* Access to an OpenShift cluster with Service Mesh 3 installed
* Cluster administrator or project administrator permissions
* The `oc` CLI tool installed and configured
* A project namespace where you can deploy applications
* The `istioctl` CLI, matching your control plane version (used in Exercise 3 and in Module 4)

=== Installing istioctl

Check the version of the Istio control plane running on the cluster:

[source,bash]
----
oc get istiorevision
----

Download the matching `istioctl` release (replace `1.28.1` if your control plane reports a different minor version):

[source,bash]
----
curl -sL https://github.com/istio/istio/releases/download/1.28.1/istioctl-1.28.1-linux-amd64.tar.gz \
  | tar xz -C /tmp
mkdir -p ~/.local/bin && mv /tmp/istioctl ~/.local/bin/istioctl
export PATH="$HOME/.local/bin:$PATH"
----

Confirm the client can reach the control plane:

[source,bash]
----
istioctl version
----

You should see a `client version`, a `control plane version` and a `data plane version`.

== Exercise 1: Enable Sidecar Injection

In this exercise, you will enable automatic sidecar injection for a namespace in OpenShift Service Mesh 3.

=== Understanding Istio CNI

Before verifying the installation, it's important to understand the role of Istio CNI (Container Network Interface) in the service mesh architecture.

Istio CNI is a critical component that handles network configuration for pods in the service mesh. Its primary purpose is to:

* *Traffic Redirection*: Sets up rules to route pod traffic through the Envoy sidecar without needing extra privileges.
* *Security*: Removes the need for `NET_ADMIN` and `NET_RAW`, making pods safer.
* *Transparency*: Automatically intercepts all pod traffic.
* *Initialization*: Prepares networking before the app starts.

Without Istio CNI, sidecar injection would require pods to run with elevated privileges. The CNI plugin configures networking securely at pod startup.

=== Step 1: Verify Service Mesh Installation

First, verify that OpenShift Service Mesh 3 is installed and all critical components are running. Check the Istio control plane pods:

[source,bash]
----
oc get pods -n istio-system
----

You should see the Istio control plane components running, including `istiod` pods. Verify they are in `Running` state:

[source,bash]
----
oc get pods -n istio-system -l app=istiod
----

Next, verify that Istio CNI is installed and running. The CNI components are deployed in the `istio-cni` namespace as DaemonSets to run on each node:

[source,bash]
----
oc get pods -n istio-cni
----

You should see Istio CNI pods running on each node in your cluster. Verify they are in `Running` state:

[source,bash]
----
oc get daemonset -n istio-cni
----

=== Step 2: Set Your Namespace

Set the `NAMESPACE` environment variable to your existing sandbox namespace. Replace `{USER}` with your actual username:

[source,bash]
----
export NAMESPACE={USER}-sandbox
----

For example, if your username is `jdoe`, your namespace would be `jdoe-sandbox`:

[source,bash]
----
export NAMESPACE=jdoe-sandbox
----

Verify that the namespace exists:

[source,bash]
----
oc get namespace $NAMESPACE
----

=== Step 3: Enable Sidecar Injection

Enable automatic sidecar injection by adding the revision label to your namespace. The revision label specifies which Istio control plane revision to use for sidecar injection. Use the revision reported by `oc get istiorevision`:

[source,bash]
----
oc label namespace $NAMESPACE istio.io/rev=default
----

NOTE: The revision value should match your Istio installation revision. Run `oc get istiorevision` to list the revisions available on your cluster. On this cluster the revision is `default`.

=== Step 4: Verify Sidecar Injection Label

Verify that the revision label has been applied:

[source,bash]
----
oc get namespace $NAMESPACE --show-labels
----

You should see `istio.io/rev=default` in the labels list.

=== Step 5: Deploy a Test Application

Deploy a simple application to verify that sidecar injection is working:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: test-app
  namespace: ${NAMESPACE}
spec:
  replicas: 1
  selector:
    matchLabels:
      app: test-app
  template:
    metadata:
      labels:
        app: test-app
    spec:
      containers:
      - name: test-container
        image: nginxinc/nginx-unprivileged:alpine
        ports:
        - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: test-app
  namespace: ${NAMESPACE}
spec:
  selector:
    app: test-app
  ports:
  - port: 80
    targetPort: 8080
    name: http
EOF
----

NOTE: The `Service` is required so that other pods in the mesh can reach this workload by name (for example `http://test-app:80` in Exercise 2). Istio also uses the named port (`http`) to determine the protocol.

=== Step 6: Verify Sidecar Injection

Check that the Envoy sidecar has been injected into your pod:

[source,bash]
----
oc get pods -n $NAMESPACE -l app=test-app
----

The pod should report `2/2` in the `READY` column: your application container plus the injected `istio-proxy`.

List the containers in the pod:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app -o jsonpath='{.items[0].metadata.name}')
oc get pod -n $NAMESPACE $POD_NAME \
  -o jsonpath='{.spec.initContainers[*].name}{"\n"}{.spec.containers[*].name}{"\n"}'
----

You should see:

----
istio-validation istio-proxy
test-container
----

IMPORTANT: From Istio 1.24 onward the sidecar is injected as a *native sidecar* — a Kubernetes init container with `restartPolicy: Always` — rather than as a regular container. This is why `istio-proxy` appears in the `initContainers` list and not under `Containers:` in `oc describe pod`. The pod still reports `2/2` ready, and `oc logs -c istio-proxy` and `oc exec -c istio-proxy` work exactly as before. Native sidecars start before the application container and shut down after it, which removes the long-standing startup and job-completion race conditions of the old model.

You can confirm the sidecar is a native sidecar with:

[source,bash]
----
oc get pod -n $NAMESPACE $POD_NAME \
  -o jsonpath='{range .spec.initContainers[*]}{.name}{" restartPolicy="}{.restartPolicy}{"\n"}{end}'
----

`istio-proxy` should show `restartPolicy=Always`.

== Exercise 2: Enable Mutual TLS (mTLS)

In this exercise, you will configure mutual TLS for your namespace using OpenShift Service Mesh 3.

=== Step 1: Create a PeerAuthentication Policy

Create a PeerAuthentication resource to enable strict mTLS for your namespace:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
  namespace: ${NAMESPACE}
spec:
  mtls:
    mode: STRICT
EOF
----

This policy enforces mTLS for all traffic within your namespace.

=== Step 2: Verify PeerAuthentication Policy

Verify that the PeerAuthentication policy has been created:

[source,bash]
----
oc get peerauthentication -n $NAMESPACE
----

=== Step 3: Create a DestinationRule (Optional but Recommended)

While PeerAuthentication enables mTLS, it's a best practice to also create a DestinationRule to explicitly specify the TLS mode:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: default
  namespace: ${NAMESPACE}
spec:
  host: "*.${NAMESPACE}.svc.cluster.local"
  trafficPolicy:
    tls:
      mode: ISTIO_MUTUAL
EOF
----

This DestinationRule ensures that all services in the namespace use Istio-managed certificates for mTLS.

=== Step 4: Verify mTLS Configuration

Check the Istio configuration to verify mTLS is enabled:

[source,bash]
----
oc get peerauthentication -n $NAMESPACE -o yaml
oc get destinationrule -n $NAMESPACE -o yaml
----

=== Step 5: Test mTLS Connection

Deploy a second application to test mTLS communication:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: apps/v1
kind: Deployment
metadata:
  name: test-app-2
  namespace: ${NAMESPACE}
spec:
  replicas: 1
  selector:
    matchLabels:
      app: test-app-2
  template:
    metadata:
      labels:
        app: test-app-2
    spec:
      containers:
      - name: test-container
        image: curlimages/curl:latest
        command: ["sleep", "3600"]
EOF
----

Wait for the pod to be ready, then exec into it and test connectivity:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')
oc exec -n $NAMESPACE $POD_NAME -c test-container -- curl -v http://test-app:80
----

The connection should succeed, and you can verify in the Envoy access logs that mTLS is being used.

=== Step 6: View Envoy Access Logs

IMPORTANT: Envoy access logging is *not* enabled by default in OpenShift Service Mesh 3. Without it the `istio-proxy` container only logs control-plane messages (certificate refreshes, readiness) and you will see no request lines at all. Enable access logging for your namespace with a `Telemetry` resource before continuing. This is namespace-scoped, so it does not affect other users of the shared control plane:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: workshop-access-logs
  namespace: ${NAMESPACE}
spec:
  accessLogging:
  - providers:
    - name: envoy
EOF
----

Generate some traffic again so there is something to look at:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')
oc exec -n $NAMESPACE $POD_NAME -c test-container -- curl -s -o /dev/null http://test-app:80
----

Now check the Envoy sidecar logs:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')
oc logs -n $NAMESPACE $POD_NAME -c istio-proxy | tail -20
----

Look for log entries indicating TLS connections.

== Exercise 3: Verify mTLS Configuration

In this exercise, you will verify mTLS configuration using various methods.

=== Step 1: Check PeerAuthentication and DestinationRule Resources

Verify the mTLS policies are correctly applied by checking the resources:

[source,bash]
----
oc get peerauthentication -n $NAMESPACE -o yaml
oc get destinationrule -n $NAMESPACE -o yaml
----

This shows the PeerAuthentication and DestinationRule configurations that enforce mTLS.

=== Step 2: Verify mTLS in Envoy Configuration

Check the Envoy sidecar configuration to verify mTLS is enabled. Get the name of a pod:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app -o jsonpath='{.items[0].metadata.name}')
----

If `istioctl` is available, you can check the proxy configuration:

[source,bash]
----
istioctl proxy-config cluster $POD_NAME -n $NAMESPACE | grep -i tls
----

This shows the TLS settings for outbound clusters.

=== Step 3: Prove STRICT mTLS Is Enforced

The most direct proof that `STRICT` mode is working is that a plaintext connection which bypasses the client sidecar is rejected. Requests addressed to the *service* go through the client sidecar and are upgraded to mTLS, while requests addressed directly to the *pod IP* are not.

[source,bash]
----
CLIENT=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')
POD_IP=$(oc get pod -n $NAMESPACE -l app=test-app -o jsonpath='{.items[0].status.podIP}')

# Through the mesh - sidecar negotiates mTLS - succeeds
oc exec -n $NAMESPACE $CLIENT -c test-container -- \
  curl -s -o /dev/null -w "via mesh: HTTP %{http_code}\n" http://test-app:80

# Straight to the pod IP - plaintext - rejected by the STRICT policy
oc exec -n $NAMESPACE $CLIENT -c test-container -- \
  curl -s -o /dev/null --max-time 8 -w "direct to pod: HTTP %{http_code}\n" http://$POD_IP:8080
----

Expected output:

----
via mesh: HTTP 200
direct to pod: HTTP 503
----

The `503` confirms the inbound sidecar refused a non-mTLS connection.

=== Step 4: Verify mTLS from Application Logs

Check the Envoy access logs to verify mTLS connections. The logs should show TLS protocol information:

[source,bash]
----
POD_NAME=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')
oc logs -n $NAMESPACE $POD_NAME -c istio-proxy | grep -i tls
----

You can also check for successful mTLS handshakes in the logs.

== Summary

In these exercises, you have:

* Enabled automatic sidecar injection for a namespace
* Verified that the Envoy sidecar is injected into application pods
* Configured mutual TLS (mTLS) using PeerAuthentication and DestinationRule resources
* Tested mTLS communication between services
* Verified mTLS configuration using `istioctl`

These foundational skills will be essential as you progress through the remaining modules of this workshop.

== Troubleshooting

If you encounter issues:

* *Sidecar not injecting*: Verify the namespace revision label is correct (`istio.io/rev=<revision>`) and matches your Istio installation revision. Ensure the Istio control plane is running.
* *mTLS not working*: Ensure both PeerAuthentication and DestinationRule are properly configured
* *Connection failures*: Check that both pods have sidecars injected and are in the same namespace (or that proper policies exist for cross-namespace communication)
* *Access denied*: Verify that the Istio control plane pods (`istiod`) are running and that certificates are being issued by checking the `istiod` logs
