= Module 2: Exercises
:hardbreaks-option:

This exercise section provides hands-on practice with Istio traffic management. You will learn how to configure Gateways, create VirtualServices with various routing patterns, implement path-based routing, perform weighted traffic splitting, and combine these components for complete traffic control.

== Prerequisites

Before starting these exercises, ensure you have:

* Access to an OpenShift cluster with Service Mesh 3 (Istio >= 1.23) installed
* Your namespace (`$NAMESPACE`) configured with sidecar injection enabled (from Module 1)
* The `oc` CLI tool installed and configured
* Basic understanding of Kubernetes Services and Deployments

== Exercise 1: Create and Configure a Gateway

In this exercise, you will create a Gateway resource to allow external traffic into your service mesh.

=== Step 1: Set Your Namespace

Ensure your namespace variable is set:

[source,bash]
----
export NAMESPACE={USER}-sandbox
----

Verify the namespace exists and has sidecar injection enabled:

[source,bash]
----
oc get namespace $NAMESPACE --show-labels | grep istio.io/rev
----

=== Step 2: Verify Istio Ingress Gateway

IMPORTANT: OpenShift Service Mesh 3 does *not* install an ingress gateway for you — the Sail operator only manages the control plane (`istiod`) and the CNI. If `oc get svc -n istio-system istio-ingressgateway` returns `NotFound`, a cluster administrator must deploy one once for the whole workshop. See <<admin-ingress-gateway>> at the end of this module.

Check that the Istio ingress gateway is running:

[source,bash]
----
oc get pods -n istio-system -l app=istio-ingressgateway
----

Note the service name and external access method:

[source,bash]
----
oc get svc -n istio-system istio-ingressgateway
----

=== Step 3: Create a Basic Gateway

Create a Gateway that accepts HTTP traffic on port 80:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-gateway
  namespace: ${NAMESPACE}
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 80
      name: http
      protocol: HTTP
    hosts:
    - "*"
EOF
----

=== Step 4: Verify Gateway Creation

Verify the Gateway was created successfully:

[source,bash]
----
oc get gateway -n $NAMESPACE
----

View the Gateway configuration:

[source,bash]
----
oc get gateway my-gateway -n $NAMESPACE -o yaml
----

=== Step 5: Create a Gateway with HTTPS

Create an additional Gateway that accepts HTTPS traffic on port 443:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: my-https-gateway
  namespace: ${NAMESPACE}
spec:
  selector:
    istio: ingressgateway
  servers:
  - port:
      number: 443
      name: https
      protocol: HTTPS
    tls:
      mode: SIMPLE
      credentialName: my-tls-secret
    hosts:
    - "myapp.example.com"
EOF
----

NOTE: In a production environment, you would need to create the TLS secret referenced in the Gateway configuration.

== Exercise 2: Create VirtualServices with Basic Routing

In this exercise, you will create VirtualServices to route traffic to your services.

=== Step 1: Deploy Sample Applications

Deploy two sample applications to use for routing:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-v1-conf
  namespace: ${NAMESPACE}
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        default_type text/plain;
        return 200 "app=frontend version=v1 pod=\$hostname uri=\$request_uri\n";
      }
    }
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: backend-v1-conf
  namespace: ${NAMESPACE}
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        default_type text/plain;
        return 200 "app=backend version=v1 pod=\$hostname uri=\$request_uri\n";
      }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: ${NAMESPACE}
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
      version: v1
  template:
    metadata:
      labels:
        app: frontend
        version: v1
    spec:
      containers:
      - name: nginx
        image: nginxinc/nginx-unprivileged:alpine
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: conf
          mountPath: /etc/nginx/conf.d
      volumes:
      - name: conf
        configMap:
          name: frontend-v1-conf
---
apiVersion: v1
kind: Service
metadata:
  name: frontend
  namespace: ${NAMESPACE}
spec:
  selector:
    app: frontend
  ports:
  - port: 80
    targetPort: 8080
    name: http
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend
  namespace: ${NAMESPACE}
spec:
  replicas: 2
  selector:
    matchLabels:
      app: backend
      version: v1
  template:
    metadata:
      labels:
        app: backend
        version: v1
    spec:
      containers:
      - name: nginx
        image: nginxinc/nginx-unprivileged:alpine
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: conf
          mountPath: /etc/nginx/conf.d
      volumes:
      - name: conf
        configMap:
          name: backend-v1-conf
---
apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: ${NAMESPACE}
spec:
  selector:
    app: backend
  ports:
  - port: 80
    targetPort: 8080
    name: http
EOF
----

NOTE: Each deployment mounts a small `ConfigMap` that replaces the default nginx page with a plain-text line identifying the app, its version and the pod that served the request, for example `app=frontend version=v1 pod=frontend-55fbf59ccd-gzzqn uri=/`. Without this every workload returns the identical default nginx welcome page and the routing, load-balancing and traffic-splitting exercises later in this workshop cannot be verified.

Wait for the pods to be ready:

[source,bash]
----
oc get pods -n $NAMESPACE -l app=frontend
oc get pods -n $NAMESPACE -l app=backend
----

=== Step 2: Create a Basic VirtualService

Create a VirtualService that routes all traffic to the frontend service:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend
  namespace: ${NAMESPACE}
spec:
  hosts:
  - frontend
  http:
  - route:
    - destination:
        host: frontend
      weight: 100
EOF
----

----

[source,bash]

== Exercise 3: Implement Path-Based Routing

In this exercise, you will create a VirtualService that routes traffic based on URI paths.

=== Step 1: Create a Path-Based VirtualService

Create a VirtualService that routes different paths to different services:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: myapp
  namespace: ${NAMESPACE}
spec:
  hosts:
  - myapp.example.com
  gateways:
  - my-gateway
  http:
  - match:
    - uri:
        prefix: "/api"
    route:
    - destination:
        host: backend
      weight: 100
  - match:
    - uri:
        prefix: "/"
    route:
    - destination:
        host: frontend
      weight: 100
EOF
----

This VirtualService:
* Routes requests to `/api/*` to the backend service
* Routes all other requests to the frontend service

=== Step 2: Verify Path-Based Routing

Check the VirtualService configuration:

[source,bash]
----
oc get virtualservice myapp -n $NAMESPACE -o yaml
----

=== Step 3: Test Path-Based Routing

Get the ingress gateway external address:

[source,bash]
----
INGRESS_HOST=$(oc get svc -n istio-system istio-ingressgateway -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
echo $INGRESS_HOST
----

If no external address is available, you can use port-forwarding:

[source,bash]
----
oc port-forward -n istio-system svc/istio-ingressgateway 8080:80 &
----

Test the frontend route:

[source,bash]
----
curl -H "Host: myapp.example.com" http://localhost:8080/
----

Test the backend API route:

[source,bash]
----
curl -H "Host: myapp.example.com" http://localhost:8080/api
----

=== Step 4: Create More Complex Path Matching

Create a VirtualService with multiple path patterns:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: complex-routing
  namespace: ${NAMESPACE}
spec:
  hosts:
  - complex.example.com
  gateways:
  - my-gateway
  http:
  - match:
    - uri:
        exact: "/api/v1/users"
    route:
    - destination:
        host: backend
      weight: 100
  - match:
    - uri:
        prefix: "/api/v2"
    route:
    - destination:
        host: backend
      weight: 100
  - match:
    - uri:
        regex: "^/static/.*\\.(jpg|png|gif)$"
    route:
    - destination:
        host: frontend
      weight: 100
  - route:
    - destination:
        host: frontend
      weight: 100
EOF
----

This example demonstrates:
* Exact path matching (`/api/v1/users`)
* Prefix matching (`/api/v2/*`)
* Regex matching (static image files)
* Default route (catch-all)

== Exercise 4: Implement Weighted Traffic Splitting

In this exercise, you will implement weighted traffic splitting for canary deployments.

=== Step 1: Deploy Multiple Versions

Deploy a second version of the frontend application:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: frontend-v2-conf
  namespace: ${NAMESPACE}
data:
  default.conf: |
    server {
      listen 8080;
      location / {
        default_type text/plain;
        return 200 "app=frontend version=v2 pod=\$hostname uri=\$request_uri\n";
      }
    }
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend-v2
  namespace: ${NAMESPACE}
spec:
  replicas: 2
  selector:
    matchLabels:
      app: frontend
      version: v2
  template:
    metadata:
      labels:
        app: frontend
        version: v2
    spec:
      containers:
      - name: nginx
        image: nginxinc/nginx-unprivileged:alpine
        ports:
        - containerPort: 8080
        volumeMounts:
        - name: conf
          mountPath: /etc/nginx/conf.d
      volumes:
      - name: conf
        configMap:
          name: frontend-v2-conf
EOF
----

Wait for the new pods to be ready:

[source,bash]
----
oc get pods -n $NAMESPACE -l app=frontend
----

=== Step 2: Create DestinationRule with Subsets

Create a DestinationRule to define service subsets (versions):

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: frontend
  namespace: ${NAMESPACE}
spec:
  host: frontend
  subsets:
  - name: v1
    labels:
      version: v1
  - name: v2
    labels:
      version: v2
EOF
----

Verify the DestinationRule:

[source,bash]
----
oc get destinationrule -n $NAMESPACE
oc get destinationrule frontend -n $NAMESPACE -o yaml
----

=== Step 3: Create VirtualService with Weighted Splitting

IMPORTANT: In Exercise 2 you created a VirtualService named `frontend` for the host `frontend`. Two VirtualServices that claim the *same host* on the mesh gateway conflict, and Istio's merge order is undefined — in practice the weights below are silently ignored and traffic is spread evenly over all four pods instead. Delete the earlier VirtualService first:

[source,bash]
----
oc delete virtualservice frontend -n $NAMESPACE
----

You can confirm there is no conflict at any point with:

[source,bash]
----
istioctl analyze -n $NAMESPACE
----

A conflict is reported as `IST0109 ... define the same host ... which can lead to undefined behavior`.


Create a VirtualService that splits traffic 90% to v1 and 10% to v2:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend-canary
  namespace: ${NAMESPACE}
spec:
  hosts:
  - frontend
  http:
  - route:
    - destination:
        host: frontend
        subset: v1
      weight: 90
    - destination:
        host: frontend
        subset: v2
      weight: 10
EOF
----

=== Step 4: Test Weighted Traffic Splitting

Send multiple requests and observe the traffic distribution. You can check the Envoy access logs to see which version receives each request:

Because each version returns its own identity string, you can count the split directly. Run the requests from a pod that is already inside the mesh — starting 100 short-lived `oc run` pods is slow and each one needs its own sidecar:

[source,bash]
----
CLIENT=$(oc get pod -n $NAMESPACE -l app=test-app-2 -o jsonpath='{.items[0].metadata.name}')

oc exec -n $NAMESPACE $CLIENT -c test-container -- \
  sh -c 'for i in $(seq 1 100); do curl -s http://frontend; done' \
  | grep -oE 'version=v[12]' | sort | uniq -c
----

With weights of 90/10 you should see roughly:

----
     92 version=v1
      8 version=v2
----

NOTE: The split is statistical, not exact — expect a few percent of variation over 100 requests. Weighted routing is applied per request by the *client* sidecar.

You can also confirm which pods served the traffic in the access logs:

[source,bash]
----
oc logs -n $NAMESPACE -l app=frontend,version=v1 -c istio-proxy --tail=10
oc logs -n $NAMESPACE -l app=frontend,version=v2 -c istio-proxy --tail=10
----

=== Step 5: Adjust Traffic Weights

Update the VirtualService to increase traffic to v2 (50/50 split):

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend-canary
  namespace: ${NAMESPACE}
spec:
  hosts:
  - frontend
  http:
  - route:
    - destination:
        host: frontend
        subset: v1
      weight: 50
    - destination:
        host: frontend
        subset: v2
      weight: 50
EOF
----

=== Step 6: Complete Canary Deployment

Finally, route 100% of traffic to v2:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend-canary
  namespace: ${NAMESPACE}
spec:
  hosts:
  - frontend
  http:
  - route:
    - destination:
        host: frontend

== Summary

In these exercises, you have:

* Created and configured Gateways to accept external traffic
* Created VirtualServices with basic routing patterns
* Implemented path-based routing to direct traffic based on URI paths
* Configured weighted traffic splitting for canary deployments
* Combined Gateways and VirtualServices for complete external traffic management
* Used DestinationRules to define service subsets for version-based routing

These skills form the foundation of Istio traffic management and are essential for implementing advanced deployment strategies in production environments.

== Troubleshooting

If you encounter issues:

* *Gateway not accepting traffic*: Verify the Gateway selector matches your ingress gateway pods and check that the gateway pods are running
* *VirtualService not routing*: Ensure the VirtualService hosts match the Gateway hosts, and verify the destination services exist
* *Traffic not splitting correctly*: Check that DestinationRule subsets match the pod labels, and verify the weight percentages sum to 100
* *External access not working*: Verify the ingress gateway service has an external IP or use port-forwarding for testing
* *Path matching not working*: Check the match conditions are correct and that routes are ordered properly (most specific first)

== Appendix: Administrator Setup — Ingress Gateway

These steps are performed *once per cluster* by an administrator, not by each workshop participant.

=== Deploy the ingress gateway

Service Mesh 3 supports *gateway injection*: you create an ordinary `Deployment` with the annotation `inject.istio.io/templates: gateway` and `image: auto`, and `istiod` replaces the placeholder with the correct Red Hat proxy image for the running control-plane revision. This keeps the gateway and the control plane on exactly the same version.

[source,bash]
----
oc apply -f - <<EOF
apiVersion: v1
kind: ServiceAccount
metadata:
  name: istio-ingressgateway
  namespace: istio-system
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: istio-ingressgateway
  namespace: istio-system
spec:
  replicas: 1
  selector:
    matchLabels:
      istio: ingressgateway
  template:
    metadata:
      annotations:
        inject.istio.io/templates: gateway
      labels:
        app: istio-ingressgateway
        istio: ingressgateway
        sidecar.istio.io/inject: "true"
        istio.io/rev: default
    spec:
      serviceAccountName: istio-ingressgateway
      containers:
      - name: istio-proxy
        image: auto
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: [ALL]
          runAsNonRoot: true
          seccompProfile:
            type: RuntimeDefault
---
apiVersion: v1
kind: Service
metadata:
  name: istio-ingressgateway
  namespace: istio-system
  labels:
    istio: ingressgateway
spec:
  type: LoadBalancer
  selector:
    istio: ingressgateway
  ports:
  - name: status-port
    port: 15021
    targetPort: 15021
  - name: http2
    port: 80
    targetPort: 8080
  - name: https
    port: 443
    targetPort: 8443
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: istio-ingressgateway-sds
  namespace: istio-system
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "watch", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: istio-ingressgateway-sds
  namespace: istio-system
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: istio-ingressgateway-sds
subjects:
- kind: ServiceAccount
  name: istio-ingressgateway
EOF
----

NOTE: The pod labels are deliberately `istio: ingressgateway` (used by the `Gateway` resource `selector` throughout this module) *and* `app: istio-ingressgateway` (used by the `oc get pods -l app=istio-ingressgateway` commands). The injection template needs `istio.io/rev` on the pod so that `istio-system` itself does not have to be labelled for injection.

Verify:

[source,bash]
----
oc get pods -n istio-system -l app=istio-ingressgateway
oc get svc -n istio-system istio-ingressgateway
----

=== Provide a LoadBalancer address (bare-metal clusters)

On a bare-metal cluster there is no cloud load balancer, so the `Service` above stays `<pending>` forever. MetalLB assigns it an address from a pool on the node network.

Install the operator:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: v1
kind: Namespace
metadata:
  name: metallb-system
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: metallb-operator
  namespace: metallb-system
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: metallb-operator-sub
  namespace: metallb-system
spec:
  channel: stable
  name: metallb-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Automatic
EOF
----

IMPORTANT: The `OperatorGroup` must have *no* `spec.targetNamespaces`. If you scope it to `metallb-system` the install mode becomes `OwnNamespace`, which the MetalLB operator does not support, and the CSV fails with `UnsupportedOperatorGroup: OwnNamespace InstallModeType not supported`.

Then create the MetalLB instance and an address pool. Choose a range on the node subnet that is not in use by any host, DHCP scope, or another cluster:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: metallb.io/v1beta1
kind: MetalLB
metadata:
  name: metallb
  namespace: metallb-system
---
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: workshop-pool
  namespace: metallb-system
spec:
  addresses:
  - 172.16.2.210-172.16.2.229
  autoAssign: false
  avoidBuggyIPs: true
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: workshop-l2
  namespace: metallb-system
spec:
  ipAddressPools:
  - workshop-pool
EOF
----

NOTE: `autoAssign: false` keeps the pool from handing addresses to unrelated `LoadBalancer` services that already exist on the cluster in a `<pending>` state. Services that should draw from the pool ask for it by name with an annotation.

Bind the gateway service to the pool:

[source,bash]
----
oc annotate svc istio-ingressgateway -n istio-system \
  metallb.universe.tf/address-pool=workshop-pool --overwrite
oc get svc istio-ingressgateway -n istio-system
----

`EXTERNAL-IP` should now show an address from the pool.

TIP: MetalLB in L2 mode answers ARP for the address but does not respond to ICMP, so `ping` to the `EXTERNAL-IP` fails even when everything works. Test with the gateway's status port instead: `curl http://<EXTERNAL-IP>:15021/healthz/ready` should return `200`. Port 80 only starts listening once a `Gateway` resource binds to it, so a connection refused on port 80 before Exercise 1 is expected.
